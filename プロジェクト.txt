各モデルへの具体的な指示（プロンプト）と運用ガイド
このプロジェクトで LLM を活用する際は、目的別にプロンプトの「型（テンプレ）」を用意すると再現性が上がります。以下は目的別テンプレートと使い方の例です。

1) コード変更・パッチ作成（ファイル編集依頼）
	- 目的: 既存ファイルに対して特定の変更を実装して欲しいとき
	- 必要な情報: 対象ファイルのパス、該当コードの抜粋（あるいは現在の diff）、期待する振る舞い・要件、失敗しているテストやエラーメッセージ（あれば）
	- テンプレート（例、短め）:
		「リポジトリのルートは /path/to/repo。編集対象は `component/duplicate_finder.py` の関数 `group_by_phash` です。現状の問題は X（エラーメッセージや挙動）。期待する修正は Y（振る舞いの説明）。該当箇所のコードは以下です：<コード>。変更はパッチ形式（diff）で出力してください。」
	- モデル選び: 正確なコード変更・パッチ生成は GPT-5-codex や GPT-5 系、Grok Code Fast を優先（コード品質とテスト記述を重視）。

2) バグ解析・デバッグ支援
	- 目的: 実行時エラーや想定と異なる振る舞いの原因分析
	- 必要な情報: 再現手順、コマンド、スタックトレース、ログ抜粋、最小再現コード（可能なら）
	- テンプレート:
		「再現コマンド: `python -m component.duplicate_finder --scan D:/videos`。ログの該当部分: <ログ>。期待する結果: Z。実際の出力: <出力>。原因と修正案を示してください。」
	- モデル選び: ログ解析や段階的推論が必要なら Claude Sonnet の Thinking 系や GPT-5 系が有利。

3) アルゴリズム設計・改善（重複判定ロジックなど）
	- 目的: スコア関数や閾値、部分一致アルゴリズムの設計
	- 必要な情報: 現状のアルゴリズム概要、サンプルデータの統計（例: ハミング距離分布）、許容誤検出率（FPR）/取りこぼし率（FNR）要件
	- テンプレート:
		「重複判定の現状ロジックは pHash のフレームサンプリング（N=16）で中央値をとる方式です。現在の閾値は 8 で、誤検出の事例がある。解像度差とトリミングに耐える部分一致アルゴリズムを設計してください。評価方法とテスト用の指標（ROC, PR曲線）も示してください。」
	- モデル選び: 設計・理論検討は GPT-4.1 / GPT-5 系や Claude 4 系が向く。

4) UI デザイン指示（画面設計や微調整）
	- 目的: レイアウト変更、要素の配置、UX 文言の作成
	- 必要な情報: 現状スクリーンショット（またはレイアウトのテキスト説明）、優先したい情報密度、ターゲット解像度
	- テンプレート:
		「デスクトップ UI（PyQt5）で、1 行最大 4 列のグリッド、カード内にサムネイル/右側に詳細/下に開く・削除ボタンを維持したい。カードの余白を 4px に抑え、折返しは自動で行う設計案を 3 つ出してください（簡潔案 + 実装メモ付き）。」
	- モデル選び: デザイン案と文書化は GPT-4.1 / Claude 4 系が適任。

5) 迅速な質問・短回答（動作確認や CLI ヘルプ生成）
	- 目的: ちょっとしたコマンドや短いヘルプ文、簡易スクリプトの生成
	- モデル選び: 03-mini / 04-mini（高速・安価）や Grok Code Fast（コードスニペット向け）を利用するとコスト効率が良い。

運用時の注意・ベストプラクティス
- コンテキストは必ず含める：対象ファイルや関連ログ、期待する出力を明記する。可能な限り最小再現ケースを添える。
- モデルの選定は「目的（コード変更／設計／短答）」で決める。重い設計は大モデル、短いスニペットや大量リクエストは軽量モデルを使う。
- セキュリティ／プライバシー：ソースコードや機密データをクラウド API に送る前に利用規約を確認する。オンプレミス実行が必要な場合はローカル実行可能なモデルを選定する。
- 出力形式の指定をする：パッチ（diff）、ユニットテスト、コマンド列など希望の出力フォーマットを明示する。

目的の要約
- 重複検出と顔グルーピングを GUI 上で提供し、ユーザーがサムネイルとメタ情報を見ながらファイル操作（開く／削除）できること。
- 重複検出は「同一作品判定」を重視し、トリミングや解像度差があっても同一作品ならグループ化すること。

UI の具体要件（表示・レイアウト）
1. カード（1 アイテム）の構成（現在のレイアウトを維持しつつ微調整）
	 - 左：サムネイル（画像／動画）
	 - 右上から順に表示：
		 • ファイルパス（最深部のフォルダ→親→…を最大 4 階層まで表示）
		 • 動画情報（動画であれば再生時間 hh:mm:ss、フレーム幅×高さ、fps 等）
		 • フォルダまたはファイルサイズ（自動で KB/MB/GB に変換）
	 - カード下部：操作列（左に「開く」、右に「削除」）
	 - パディングは控えめに（カード内 4〜8px程度）。不要な余白は削除して情報密度を保つ。

2. グループ（重複群）の配置
	 - 1 行につき最大 4 ブロックを横並びに表示。5 個目からは次の行へ折り返す（横スクロール不要）。
	 - 画面幅に応じてカードサイズを自動調整し、縦スクロールで全グループを閲覧可能にする。

重複検出ルール（実装指針）
- 判定方針：トリミング（切り抜き）や解像度差、フレーム幅／高さ差があっても「同一作品」と見なせる場合は同一グループへ。
- 実装のコアアイデア：
	- 複数フレームの pHash をサンプリングし、フレーム列の一致度（最小距離、中央値、部分一致割合など）でスコアリングする。
	- 解像度違いやトリミングの影響を緩和するために、複数スケールでの比較や、部分一致（サブシーケンス一致）を許容するアルゴリズムを採用する。
	- ファイルサイズ比やフレーム数差は補助情報として利用し、極端に小さい共通部分しかない場合は低スコア化する。

操作 UX の詳細
- サムネイルはホバーで短いプレビュー再生を表示できると便利（オプション）。
- パスの長さは 4 階層まで表示し、長い場合は省略記号で切る。
- 削除操作は必ず確認ダイアログを表示する（復元不可であればさらに注意文を出す）。

実装・運用の注意点
- キャッシュの署名管理：pHash やグルーピング結果をキャッシュする場合、サンプリング数や閾値、アルゴリズムバージョンをキャッシュキーに含め、ロジック変更時に自動で無効化できるようにする。
- 診断ツール：疑わしいグループが出たときに、サンプリングした pHash のハミング距離分布や代表フレームの比較を出力する診断機能を必ず用意する（既存の診断スクリプトを活用可）。
- テストケース：
	- トリミングされた動画（切り抜き）でも同一グループに入るか
	- 解像度・フレーム数が異なる同一ソースのファイルがグループ化されるか
	- キャッシュを削除／無効化した状態で再現性があるか

結び（要点）
- 実装は「PyQt5 に精通した Python エンジニア」を中心に進めるのが適切です。
- 重複判定は「同一作品性」を重視し、pHash の時系列比較＋部分一致許容を採用してください。キャッシュの管理と診断機能を実装して、安全で再現可能な判定を目指してください。
